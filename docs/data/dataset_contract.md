# Lock-Contention Dataset Contract

Status: Checkpoint 27 implementation baseline

Schema version: `1.0.0`

Prediction horizon: 30 seconds

## Purpose

This dataset supports supervised learning for predicting whether PostgreSQL
will experience high lock contention within the next 30 seconds.

The dataset is produced from controlled reservation experiments. Booking
requests are generated by Locust, but PostgreSQL and application metrics are
measured from real transactions executed by the project database.

The first export is a controlled pilot dataset used to validate the collection,
labelling and export pipeline. It is not the final research dataset.

A later dataset version will use demand profiles calibrated from a public
real-world interaction dataset.

## Unit of observation

One dataset row represents one complete `metric_samples` record collected at
a particular timestamp during one experiment.

Every row is identified by:

- `experiment_run_id`
- `sampled_at`

Rows belonging to different experiments must never be treated as though they
came from one continuous time series.

## Data provenance

Every exported row must be traceable to:

- one completed experiment
- one experiment configuration
- one metric sample
- one collector version
- one code version
- one dataset schema version
- one immutable export file
- one SHA-256 checksum

The experiment ID connects:

- workload configuration
- booking attempts
- PostgreSQL metrics
- application metrics
- labels
- audit events
- exported datasets

## Experiment eligibility

An experiment may be exported only when:

1. The experiment exists.
2. Its status is `COMPLETED`.
3. It contains metric samples.
4. All exported samples belong to that experiment.
5. Required samples have `is_complete = true`.
6. The experiment uses a supported booking mode.
7. Its workload and collector processes finished successfully.

Smoke tests and debugging experiments should not be included in the final
training dataset.

## Observation window

Features are taken only from the current metric sample at time `t`.

No future value may be included as a model feature.

The future prediction window is:

`(t, t + 30 seconds]`

The current sample at exactly `t` is not part of its own future label.

## Primary target

The primary binary target is:

`future_high_contention_30s`

Possible values:

- `0`: no high-contention condition occurs in the following 30 seconds
- `1`: at least one high-contention condition occurs in the following
  30 seconds

## High-contention definition

A future sample is considered high contention when at least one of these
conditions is true:

1. `blocked_sessions >= 2`
2. `waiting_locks >= 2`
3. `deadlock_delta >= 1`
4. `timeout_rate > 0`

The target for a row is positive when any eligible future sample inside the
30-second horizon satisfies at least one condition.

Latency alone does not define lock contention. High p95 latency is retained as
supporting evidence but is not sufficient by itself to create a positive lock
contention label.

## Label evidence columns

The exporter must calculate these future-window evidence columns:

- `future_max_blocked_sessions_30s`
- `future_max_waiting_locks_30s`
- `future_deadlock_delta_sum_30s`
- `future_max_timeout_rate_30s`
- `future_max_p95_latency_ms_30s`
- `future_high_contention_30s`

Future evidence columns are used for label validation and research analysis.

They must never be supplied to the prediction model as input features.

## Complete-horizon requirement

A row is eligible only when a complete 30-second future window exists within
the same experiment.

For a row collected at time `t`, the experiment must contain samples through
at least:

`t + 30 seconds`

Rows from the final 30 seconds of an experiment normally have incomplete
future horizons and must be excluded.

The exporter must never create negative labels merely because future samples
are missing.

## Metadata columns

The exported dataset must contain these metadata columns:

- `schema_version`
- `experiment_run_id`
- `experiment_name`
- `sampled_at`
- `collector_version`
- `code_version`
- `booking_mode`
- `random_seed`
- `sample_interval_sec`
- `simulated_work_ms`
- `is_complete`
- `quality_notes`

Metadata columns support traceability and analysis.

They are not automatically model features.

## Candidate model features

The initial candidate feature set contains only information available at or
before the prediction timestamp:

### PostgreSQL features

- `active_transactions`
- `blocked_sessions`
- `waiting_locks`
- `total_locks`
- `total_connections`
- `connection_utilization`
- `estimated_wait_age_ms`
- `deadlock_delta`

### Application and workload features

- `configured_users`
- `active_users`
- `requests_per_sec`
- `mean_latency_ms`
- `p95_latency_ms`
- `failure_rate`
- `hotspot_ratio`
- `booking_success_rate`
- `conflict_rate`
- `timeout_rate`

The final feature set will be selected during the machine-learning phase.

Experimental configuration fields such as `simulated_work_ms`, `random_seed`
and `code_version` must remain metadata. They must not be used as model
features because they are experimental controls rather than normal
production telemetry.

## Data-quality requirements

Every eligible row must satisfy:

1. `experiment_run_id` is present.
2. `sampled_at` is present.
3. `is_complete` is true.
4. Required model features are not null.
5. Count values are nonnegative.
6. Latency and throughput values are nonnegative.
7. Rate values are between zero and one.
8. The future horizon is complete.
9. The target is either zero or one.
10. Future evidence comes only from the same experiment.
11. Rows are ordered by experiment and timestamp.
12. Duplicate `(experiment_run_id, sampled_at)` rows do not exist.

Rows failing these requirements must be rejected or explicitly reported.

## Export structure

The project uses two export levels.

### Per-experiment export

Each completed experiment is exported to an immutable CSV file.

Suggested path:

`data/exports/experiments/<experiment_run_id>.csv`

Each per-experiment export is registered in `data_exports` with:

- experiment ID
- file path
- SHA-256 checksum
- schema version
- row count
- creator
- creation timestamp

Only one registered export is permitted for each experiment under the current
database schema.

### Combined pilot dataset

Approved per-experiment exports are combined into:

`data/processed/pilot_contention_dataset_v1.csv`

A manifest must identify:

- included experiment IDs
- source export paths
- source checksums
- combined row count
- schema version
- combined checksum
- creation timestamp

The combined file is a derived dataset. Per-experiment exports remain its
authoritative sources.

## Dataset splitting rule

Rows must not be randomly split without considering experiment boundaries.

All rows from one `experiment_run_id` must belong to only one of:

- training data
- validation data
- test data

This prevents nearly identical neighbouring samples from the same experiment
appearing in both training and testing data.

The pilot dataset is used to validate the pipeline and will not yet be treated
as the final train/test dataset.

## Pilot experiment matrix

Checkpoint 27 should initially run at least three synchronized experiments.

### Low-contention pilot

- users: 3 to 5
- low hotspot concentration
- simulated work: 20 to 50 milliseconds
- expected result: mostly negative labels

### Medium-contention pilot

- users: approximately 10
- medium hotspot concentration
- simulated work: approximately 150 milliseconds
- expected result: a mixture of negative and positive labels

### High-contention pilot

- users: approximately 20
- high hotspot concentration
- simulated work: approximately 350 milliseconds
- expected result: more positive labels

Each pilot should run for at least 90 seconds.

A 30-second experiment is insufficient for useful 30-second future labels
because its final 30 seconds do not have a complete prediction horizon.

The final research dataset will require more experiments, multiple random
seeds and real-world-calibrated demand profiles.

## Pilot acceptance criteria

The Checkpoint 27 pilot dataset is accepted only when:

1. At least three completed experiments are included.
2. Low, medium and high workload scenarios are represented.
3. Every included experiment has synchronized metric and workload data.
4. At least 60 eligible labelled rows exist across the pilot experiments.
5. Both target classes, zero and one, are present.
6. No required feature contains null values.
7. Every row has a complete 30-second future horizon.
8. No experiment contributes rows to more than one data split.
9. Per-experiment checksums are valid.
10. The combined dataset checksum is valid.
11. Export row counts match the corresponding files.
12. Automated label and exporter tests pass.

If both target classes are not present, workload settings must be adjusted and
the experiments repeated. Labels must never be manually changed to manufacture
class balance.

## Leakage prevention

The following are prohibited as model inputs:

- future evidence columns
- the target column
- experiment completion status
- experiment end timestamp
- post-experiment aggregates
- manually assigned scenario labels
- file names or export identifiers
- values calculated using samples after the prediction timestamp

Feature engineering must use only present and historical information.

## Real-world calibration plan

The initial controlled pilot validates the technical pipeline.

A later phase will incorporate a public real-world interaction dataset to
derive realistic:

- popularity distributions
- high-demand and low-demand profiles
- temporal activity patterns
- request-frequency profiles
- hotspot-selection probabilities

The public data will configure experimental demand. PostgreSQL telemetry will
remain the authoritative source for lock-contention features and labels.

## Limitations

The pilot dataset is generated on one local development machine and one
PostgreSQL instance.

It demonstrates controlled concurrency and measured lock behaviour but does
not by itself prove generalization to:

- production hardware
- geographically distributed services
- other database engines
- different transaction schemas
- real customer booking traffic

These limitations must be stated in the final report.
